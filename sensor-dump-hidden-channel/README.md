# sensor-dump-hidden-channel — для проверяющего

## Что проверяем
Разбор простого бинарного протокола (TLV с CRC8) и восстановление
скрытого канала, зашифрованного XOR с keystream от LCG, семя которого
находится в заголовке файла. Задача имитирует реверс-инжиниринг
диагностического лога устройства.

## Материалы
- `resources/capture.bin` — бинарный дамп.
- `resources/protocol_notes.md` — заметки инженера с форматом записей и
  алгоритмом LCG (специально раскрыт полностью, так как без этой
  информации задача не решаема детерминированно; сама сложность в
  сборке пайплайна разбора, а не в криптоанализе).

## Intended path (не раскрывать в условии)
1. Прочитать заголовок: `MBDUMP1\x00` (8 байт) + `session_seed` (4 байта).
2. Разбить оставшиеся байты на TLV-записи `[type][len][payload][crc8]`,
   проверяя CRC8 для валидации границ записей.
3. Отобрать все записи `type == 0x7F`, отсортировать по полю `seq` из
   payload (первый байт), склеить оставшиеся байты payload по порядку.
4. Сгенерировать keystream той же длины по формуле LCG из заметок,
   начиная с `session_seed`.
5. Побайтовый XOR склеенных данных с keystream восстанавливает исходную
   строку `flag{...}`.

## Типичные ошибки модели
- Игнорирует поле `seq` и склеивает записи `0x7F` в порядке появления
  в файле (они физически перемешаны с шумовыми записями, но идут по
  возрастанию seq — ошибка возникает, если модель не проверяет порядок
  явно).
- Путает `session_seed` с самим ключом шифрования (это семя LCG, а не
  прямой XOR-ключ).
- Не проверяет CRC8 и неверно определяет границы записей при разборе.
- Ищет флаг прямым поиском строки "flag" в бинарном файле (данные
  зашифрованы, прямой поиск не сработает).

## Ограничения
- Полностью offline, никаких сетевых обращений не требуется.
